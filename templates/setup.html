One-time Google Cloud setup

Google requires every app that touches your YouTube account to run inside a Cloud project you control. Four steps, once, roughly ten minutes.

  1. 1

    Create a project and enable the API

    In the Google Cloud Console, create a project — any name. Then search the menu for YouTube Data API v3 and enable it for that project.

    Do not point another tool at the same project — this app can only count its own calls, so a second tool's spending would make the remaining figure read higher than the truth, and playlist mirrors would hit the wall earlier than predicted.

  2. 2

    Add yourself as a test user

    Under APIs & Services, open OAuth consent screen — called Audience in newer consoles. In Test users, click + Add users and enter the Google address you will sign in with.

    Skipping this is what produces Error 403: access_denied — has not completed the Google verification process. While the app's status is Testing, only listed test users can sign in. There is no approval wait; access is immediate.

  3. 3

    Create an OAuth client and add its file here

    In Credentials, choose Create credentials → OAuth client ID. Pick the application type that matches how you reach this app: Desktop app if that is localhost, Web application for any other address. Download the JSON and add it below. It is written to this instance's data volume as client_secret.json and never leaves this machine.

    Desktop-app clients accept any http://localhost redirect without registration — and only those. They cannot have any other redirect URI registered at all, so a desktop client that worked on localhost will fail with redirect_uri_mismatch once you host this elsewhere. For any other address use a Web application client, add this exact redirect URI under Authorized redirect URIs: {{ conn.redirect_uri }} — and set PUBLIC_BASE_URL to match. Google requires that URI to be https:// on a real public TLD; the host itself does not have to be reachable from the internet, only from your browser.

  4. 4

    Sign in

    Google asks for permission to manage your YouTube account. The resulting token is stored in the data volume, so this is a one-time step.

When sign-in goes wrong

A handful of failures account for nearly all of them.

“Error 400: redirect_uri_mismatch”
Google was sent a redirect URI the OAuth client does not accept. The one this instance sends is {{ conn.redirect_uri }} — it must appear, character for character, under Authorized redirect URIs on the client in APIs & Services → Credentials. Two things to check: that PUBLIC_BASE_URL is set to the address you actually open this app at (an unset one leaves it at http://localhost:8000, which is what gets sent from behind a reverse proxy), and that the client is a Web application one — a Desktop app client cannot register anything but http://localhost, so it works locally and breaks everywhere else.
“Error 403: access_denied”
The account you signed in with is not a test user on that project. Add it in step 2, and check you are adding it under the same project that owns the OAuth client. An incognito window rules out signing in as a different cached account.
The browser shows “connection refused” after signing in
Nothing is listening on the redirect address. Confirm the container publishes its port (ports: "8000:8000") and that PUBLIC_BASE_URL matches the address you actually opened this page at — currently {{ conn.redirect_uri }}.
Sign-in loads a stale page from some other app
A service worker from a previous app on the same port is intercepting the callback. Clear site data for that origin, use a private window, or move this app to a port nothing else has ever used.
